# 부하 테스트 / 성능 측정 계획

지금까지의 k6 테스트는 **정합성**을 검증했다(오버셀 없음, 데드락 없음 — 실제로
데드락 버그를 하나 잡았다. `README.md` 참고). 이 문서는 그다음 단계, **성능
특성과 한계를 실측으로 설명하는 것**의 계획서다.

측정 목표는 절대 성능 수치가 아니다. 측정 환경(1절)의 제약 때문에 "초당 N건"
같은 절대값은 이 환경에서 도출할 수 없다. **동일 조건에서 조건 하나만 바꿔
A와 B를 비교**하고, 어떤 설계 선택이 어떤 결과를 낳는지 설명하는 것이 목표다.

---

## 1. 측정 환경과 그 한계

### 구성

k6, Spring Boot 앱, MySQL이 **전부 같은 PC**에서 실행된다. 서버 설정은 명시적
오버라이드 없이 대부분 기본값을 쓴다.

| 항목 | 값 | 출처 |
|---|---|---|
| HikariCP `maximumPoolSize` | 10 | 기본값 — **actuator `hikaricp.connections.max`로 실측 확인** |
| Tomcat `threads.max` | 200 | 기본값 — **actuator `tomcat.threads.config.max`로 실측 확인** |
| MyBatis `defaultStatementTimeout` | 30초 | `application.yml` |
| MyBatis `defaultFetchSize` | 100 | `application.yml` |

(앞의 두 값은 "Spring Boot 기본값이니 그럴 것"이라는 추정이었는데, 관측성 작업 후
실제 서버에서 조회해 확정했다. 통합 테스트 프로파일은 예외로
`application-integration.yml`이 풀을 30으로 올려 쓴다.)

### 이 구성에서 나오는 수치의 한계

1. **절대 수치는 쓸 수 없다.** VU가 커질수록 k6 자체가 CPU를 두고 앱·MySQL과
   경쟁한다. "이 서버는 초당 N건을 처리한다"는 결론은 이 환경에서 나올 수 없다.
2. **상대 비교만 유효하다.** 같은 환경에서 조건 하나만 바꿔 측정한 두 결과의
   차이는 의미가 있다. 기존 `02` vs `02b`(파트너 공유 vs 분산)가 이미 이 원칙을
   따르고 있다. 앞으로 추가하는 시나리오도 전부 **대조군을 짝지어** 설계한다.
3. 부하 생성기를 다른 PC로 분리할 수 있게 되면 1번 제약이 사라진다. 가능해지면
   그때 재측정하고, 그 전까지는 모든 결과에 이 한계를 명시한다.

### 실행 규칙

- 비교 대상 두 시나리오를 **동시에 실행하지 않는다.** 순차 실행하되 같은 시간대에.
- 실행 전 8080 포트에 이전 인스턴스가 남아있지 않은지 확인한다.
- **워밍업 구간(첫 20초 내외)은 판정에서 제외한다.** JIT 컴파일과 커넥션 풀 초기
  생성 때문에 항상 느리다. 포함하면 모든 결과가 비관적으로 왜곡된다.
- `k6/reports/*.html`은 실행할 때마다 덮어써진다. 비교할 결과는 실행 직후 다른
  이름으로 복사해둔다.

## 2. 판정 기준

기준을 먼저 정해두지 않으면 그래프를 보고 사후에 끼워맞추게 된다.

### SLO

| 지표 | 기준 |
|---|---|
| `http_req_duration` p95 | < 500ms |
| `sale_server_error_rate` (5xx) | 0 |
| `sale_connection_error_rate` (연결 실패/타임아웃) | 0 |
| `sale_client_error_rate` (400/404) | 0 — 0이 아니면 서버가 아니라 **스크립트** 결함 |

이 기준을 처음 벗어나는 지점을 **한계점**으로 정의한다.

현재 `02-load.js`의 threshold는 `http_req_duration: p(95)<2000`으로 위 기준보다
느슨하다. 의도적으로 어긋나 있는 것이 아니라 SLO를 정하기 전에 잡은 값이므로,
정렬 여부를 판단해야 한다. load 단계는 여유를 두고 breakpoint 탐색에서만 500ms를
적용하는 선택지도 있다 — 관측성 확보 후 실제 분포를 보고 결정한다.

### 실패로 세지 않는 것

- **409 락 충돌**: 정상 비즈니스 분기다. 다만 비율이 치솟으면 그 락 전략의 실용
  한계 신호이고, 이것이 A1 비교의 핵심 지표가 된다.
- **409 재고 부족**: 마찬가지로 정상. `01-smoke.js`는 의도적으로 이걸 유발한다.

### 포화점 판정

Little's law(동시성 = 처리량 × 응답시간)에 따라, VU를 늘렸는데 **처리량은 정체되고
응답시간만 비례해서 증가**하면 그 직전이 포화점이다. VU 구간별 `http_reqs` rate와
`http_req_duration` p95를 나란히 놓고 판정한다.

## 3. 관측 지표

### 클라이언트측 — 구현 완료

`helpers.js`의 `classifyResponse()`가 응답마다 채운다. 상세는 `README.md`의
"결과 읽는 법" 참고.

### 서버측 — 구현 완료 ✅

원래 서버 내부를 볼 수단이 전혀 없어서(actuator 의존성 자체가 없었음) "VU 80에서
느려졌다"까지만 알 수 있고 **"왜"는 추측**이었다. actuator를 도입해 해결했다.

**수집 방식**: 별도 수집 파이프라인이나 CSV 정렬 없이, **부하와 같은 k6 실행 안에서
`server_probe` 시나리오(1 VU, 1초 간격)가 actuator를 폴링**한다. 같은 리포트에 같은
시간축으로 남으므로 "응답시간이 튄 구간에 풀이 말라 있었는지"를 바로 볼 수 있다.
구현은 `helpers.js`의 `sampleServerMetrics()`, 적용 대상은 `02`/`02b`/`03`/`03b`
(`01-smoke.js`는 요청 3건짜리 정합성 확인이라 서버 지표가 의미 없어 제외).

| k6 지표 | actuator 원본 | 무엇을 판정하나 |
|---|---|---|
| `server_hikari_active` | `hikaricp.connections.active` | 풀을 실제로 얼마나 쓰는가 |
| `server_hikari_pending` | `hikaricp.connections.pending` | **0보다 크면 풀이 병목** |
| `server_tomcat_busy` | `tomcat.threads.busy` | 요청이 스레드 레벨에서 밀리는가 |
| `server_heap_used_mb` | `jvm.memory.used` | 힙이 계속 증가하는가(누수) |

**주의 두 가지** (스크립트 주석에도 적어둠):
1. 폴링 요청도 `http_req_duration`에 잡힌다. 부하 쪽 임계값은 반드시
   `http_req_duration{scenario:...}`로 범위를 좁혀야 한다 — 안 좁히면 훨씬 빠른
   폴링 요청이 섞여 p95가 실제보다 낙관적으로 나온다(실측으로 확인: 전체 24.23ms
   vs 부하 시나리오만 24.44ms).
2. `tomcat.threads.busy`에는 폴링 요청 자신이 상시 1건 포함된다.

**아직 안 되는 것**: MySQL 쪽(`Threads_running`, 락 대기)은 actuator로 잡히지
않는다. 앱이 아니라 DB가 병목으로 의심되면 그때 `SHOW ENGINE INNODB STATUS`
계열을 별도로 붙인다(데드락 조사 때 쓴 방법과 동일).

`jvm.gc.pause`도 노출은 되지만 Trend로 수집하진 않는다 — GC가 응답시간 튐의
원인으로 의심될 때 추가한다.

## 4. 시나리오 로드맵

상태: ⬜ 미착수 · 🟦 진행중 · ✅ 완료

### 기존 — 정합성 검증 (완료)

| # | 파일 | 목적 | 상태 |
|---|---|---|---|
| 01 | `01-smoke.js` | 락 정합성(오버셀 없음) — 데드락 버그 발견에 사용 | ✅ |
| 02 / 02b | `02-load.js` / `02b-load-multi-partner.js` | 지속 부하, 원장 잠금 영향 분리 | ✅ |
| 03 / 03b | `03-stress.js` / `03b-stress-multi-partner.js` | 동시접속 한계 탐색 | ✅ |

### A그룹 — 쓰기 경합

| # | 시나리오 | 보려는 것 | 상태 |
|---|---|---|---|
| A1 | **낙관 vs 비관 락 정면 비교** | 같은 부하·같은 경합도에서 두 전략의 처리량 / p95 / 실패 양상 | ✅ |
| A2 | 커넥션 풀 크기 스윕 (10 / 20 / 50 / 100) | 풀을 키우면 처리량이 계속 오르는가 | ⬜ |
| A3 | 경합도 스윕 (규격 1개 vs N개) | 핫 로우 경합이 처리량에 미치는 영향 곡선 | ⬜ |

**A1** — 4단계에서 전략 패턴으로 두 구현을 다 만들어놨지만, `SaleController`가
`@Qualifier("optimisticLockSaleService")`로 고정되어 있어 비관적 락은 HTTP로 접근할
수 없다(`README.md` "중요한 한계"). 부하 비교가 막혀 있는 상태다.

핵심은 "어느 쪽이 빠른가"가 아니라 **"어떻게 다르게 망가지는가"**다. 낙관적 락은
충돌 시 재시도(CPU 소모 + 409 반환)로, 비관적 락은 대기(스레드 점유 → 풀 고갈)로
각각 다르게 무너진다. 경합도를 올려가며 두 곡선을 겹쳐 그리는 것이 목표다.

**완료 (2026-08-16). 결과는 `README.md`의 "A1" 절 참고.** 요약하면, 응답시간만 보면
낙관적 락이 빠르지만 그건 요청의 87%를 409로 되돌려서 얻은 숫자이고, 실제로 끝낸
매출 건수는 비관적 락이 5.9배 많았다. 커넥션 풀·스레드 포화 정도는 양쪽이 동일해서,
자원 병목은 락 전략과 무관하고 갈리는 건 그 자원으로 무엇을 끝냈는가였다. 단
"규격 하나에 전부 몰릴 때"의 이야기라 A3(경합도 스윕)에서 역전 지점을 봐야 한다.

전환 방식은 **설정(`myerp.sale.lock-strategy`)으로 주입 대상을 바꾸는 것**을 택했다.
- 프로덕션 API 표면(URL·파라미터)을 건드리지 않는다.
- "운영 중 락 전략을 설정으로 전환한다"는 건 전략 패턴의 원래 목적에 부합한다.
- 프로파일을 바꾸려면 재기동해야 하는데, 부하 테스트에서는 이게 오히려 JIT/풀
  상태를 초기화해줘서 조건 격리에 유리하다.
- (기각) 쿼리파라미터 `?lockMode=pessimistic` 방식 — 재기동 없이 A/B가 되지만
  테스트용 파라미터가 프로덕션 API에 영구히 남는다.

**A2**에서 기대하는 그림은 처리량 곡선이 **어느 지점에서 꺾이는 것**이다. 이
프로젝트는 같은 행에 경합이 몰리는 구조라, 풀을 키우면 DB 안에서 락 대기만 늘어
오히려 나빠질 가능성이 있다. "풀은 크게 잡을수록 좋다"는 직관이 실측으로 깨지는지
확인한다. 스윕하려면 `maximum-pool-size`를 환경변수로 주입할 수 있어야 한다.

### B그룹 — 읽기 경로 (전면 미착수)

현재 5개 스크립트가 전부 `POST /api/sales` 쓰기만 때린다. 실제 ERP는 읽기가
압도적으로 많은데 측정이 전혀 없다. 그리고 코드에 이미 구조적 문제가 보인다
(`SaleMapper.xml`):

```sql
SELECT ... FROM sale ORDER BY id DESC LIMIT #{size} OFFSET #{offset}
SELECT COUNT(*) FROM sale
```

- `OFFSET`이 깊어지면 앞의 행을 전부 읽고 버린다 — 뒤 페이지일수록 느려진다.
- `COUNT(*)`가 **매 페이지 요청마다** 실행된다 — 데이터가 커지면 여기가 먼저 병목.

| # | 시나리오 | 보려는 것 | 상태 |
|---|---|---|---|
| B1 | 목록 페이징 (1페이지 vs 1000페이지) | deep offset 열화 곡선, `COUNT(*)` 비용 분리 | ⬜ |
| B2 | 원장 이력 조회 (`GET /api/partners/{id}/ledger`) | 인덱스가 있는 경로 — **B1의 대조군** | ⬜ |
| B3 | 혼합 워크로드 (읽기 9 : 쓰기 1) | 실제 사용 패턴에서 읽기와 쓰기가 서로를 방해하는가 | ⬜ |

B1과 B2를 **대조군으로 짝지어** 돌리는 것이 핵심이다. `ledger_entry`에는
`idx_ledger_entry_partner_created`가 있고 `sale` 목록 조회에는 대응 인덱스가 없으니,
같은 데이터 규모에서 비교하면 인덱스 유무의 차이가 그대로 드러난다. `EXPLAIN`
결과와 인덱스 추가 전/후 재측정을 붙이면 완결된 개선 사례가 된다.

**전제조건**: 읽기 성능은 빈 DB에서 측정하면 무의미하다. `sale` 10만~100만 건
규모의 시드가 필요하고, API로 넣으면 너무 느리니 SQL 대량 INSERT로 만든다.
**실데이터와 섞이면 안 되므로** 별도 DB(`erp_db_loadtest`)를 쓰는 방안이 가장 깔끔하다.

### C그룹 — 한계와 내구성

| # | 시나리오 | 보려는 것 | 상태 |
|---|---|---|---|
| C1 | 스파이크 (평상시 → 급증 → 복귀) | 무너진 뒤 **회복하는가** | ⬜ |
| C2 | 소크 (20~30분 일정 부하) | 커넥션/메모리 누수, 서서히 열화하는가 | ⬜ |
| C3 | 브레이크포인트 (SLO 위반까지 계속 증가) | 진짜 한계점과 무너지는 방식 | ⬜ |

**C1**이 실무적으로 가장 의미 있다. "몇 명까지 버티나"보다 **"넘긴 뒤 정상으로
돌아오나"**가 진짜 질문이고, 돌아오지 못하면 커넥션 누수나 스레드 고갈 같은
구조적 결함이 있다는 뜻이다. **C2**는 짧은 테스트로는 절대 안 보이는 종류의 결함을
잡는다. `03-stress.js`가 C3의 원형이지만 SLO 기반 자동 판정이 없다.

### D그룹 — 6단계(정산/통계) 이후

월별 집계, 거래처별 미수금 TOP N, 품목별 매출 순위 같은 집계 쿼리는 지금 존재하지
않는다. 6단계 구현 시 B그룹의 시드 데이터를 그대로 재사용해 `EXPLAIN` → 인덱스
추가 → 재측정 사이클을 돌린다.
