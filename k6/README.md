# 매출 등록(락) k6 부하 테스트

`POST /api/sales`(매출 전표 등록)가 같은 규격(item_spec)에 동시에 여러 요청이
몰려도 오버셀 없이 처리되는지를 실제 HTTP 계층에서 검증한다.

이 문서는 **지금 있는 스크립트의 사용법과 그동안 발견한 것**을 다룬다. 앞으로의
성능·한계 측정 계획(측정 환경의 한계, SLO, 시나리오 로드맵)은
[`LOAD_TEST_PLAN.md`](LOAD_TEST_PLAN.md)에 따로 정리했다.

## 전제

- 로컬 백엔드(`./gradlew bootRun`)와 MySQL(`erp_db`)이 떠 있어야 한다.
- 로그인 계정은 기본값으로 `owner@myerp.com` / `password123`을 쓴다. 다르면
  `-e TEST_EMAIL=... -e TEST_PASSWORD=...`로 오버라이드.
- 서버 주소가 `http://localhost:8080`이 아니면 `-e BASE_URL=...`로 오버라이드.
- [k6](https://k6.io) 설치 필요.
- 실행할 때 인터넷 연결 필요 — `handleSummary()`가 `jslib.k6.io`/`raw.githubusercontent.com`에서
  요약·HTML 리포트 렌더링 스크립트를 원격으로 불러온다(k6 표준 방식, 별도 설치 불필요).

## 3단계 구성

| 파일 | 이름 | 목적 | VU | 재고 |
|---|---|---|---|---|
| `01-smoke.js` | 무리가 가지 않는 상황 | 락 로직 자체의 정합성(오버셀 안 남) | 3, 1회씩 | 3(일부러 부족) |
| `02-load.js` | 견딜 수 있는 상황 | 지속 부하에서 커넥션/스레드 안 새는지 | 8, 45초 유지 | 5000(넉넉) |
| `03-stress.js` | 한계 상황 | 순수 동시접속 한계점 탐색(0→100 램프업) | 0→100 | 100000(사실상 무제한) |

각 스크립트는 실행 시작 시(`setup()`) 전용 거래처/회사정보/카테고리/품목/규격을
새로 만들어 실데이터와 절대 섞이지 않는다. 끝나면(`teardown()`) 실제 재고를
다시 조회해 **음수가 아닌지**를 자동으로 확인한다.

## 원장(5단계) 도입 이후 추가된 변형 — `02b`/`03b`

`OptimisticLockSaleService.register()`는 재고 차감 뒤 같은 트랜잭션 안에서
`LedgerService.recordReceivableChange`를 호출해 `partner.receivable_balance`를
갱신한다. item_spec 쪽은 낙관적 락(대기 없이 재시도)이지만, partner 쪽은
`UPDATE ... WHERE id=?`로 진짜 DB 행 잠금을 건다.

`02-load.js`/`03-stress.js`는 전 VU가 거래처 1개를 공유하기 때문에, 이 partner
행 잠금 경합이 item_spec 낙관적 락 성능과 뒤섞여서 측정된다. `02b-load-multi-partner.js`/
`03b-stress-multi-partner.js`는 조건은 완전히 동일하되 VU마다 서로 다른 거래처를
써서 partner 잠금 경합을 제거한다 — item_spec 재고/조건은 그대로 공유되므로
그 변수는 고정된 채로, "원장 잠금이 얼마나 발목을 잡는지"만 분리해서 본다.

`01-smoke.js`는 원래 목적(락 정합성의 경계 케이스 확인)이 파트너 분산과 무관해서
변형을 만들지 않았다.

## 실행

```bash
k6 run k6/01-smoke.js
k6 run k6/02-load.js
k6 run k6/02b-load-multi-partner.js
k6 run k6/03-stress.js
k6 run k6/03b-stress-multi-partner.js
```

순서대로 실행 권장 — smoke가 실패하면(락 정합성 자체가 깨지면) load/stress
결과는 의미가 없다. `02`/`02b`, `03`/`03b`는 같은 시간대에 동시 실행하지 말 것
(같은 서버·DB 상태를 두고 비교해야 결과가 의미 있다).

**비교하는 법**: `02`와 `02b`(또는 `03`과 `03b`)의 처리량/`http_req_duration`
p95를 나란히 보면 된다. `02b`/`03b`가 뚜렷하게 더 빠르거나 더 높은 VU까지
버틴다면, partner 원장 잠금이 실제 병목이라는 근거다 — 그 경우 "같은 거래처에
매출이 동시다발로 몰리는 게 실무에서 흔한 시나리오인지"부터 다시 따져볼
필요가 있다. 차이가 거의 없다면 병목은 원장이 아니라 HikariCP 풀/Tomcat
스레드 같은 다른 공용 자원이라는 뜻이다.

## 결과 읽는 법

지표는 전부 `helpers.classifyResponse()` 한 곳에서 채운다(스크립트마다 이름이
어긋나지 않게). 응답 하나마다 `sale_status_codes`(상태코드별 카운트)는 항상
채워지고, `sale_response_time`(Trend, `http_req_duration`과 별개로 이 도메인
전용)은 **연결 실패(status 0)를 제외한** 응답에만 기록한다 — 연결 자체가 안
된 요청의 duration은 "서버가 얼마나 빨리 응답했는가"와 무관해서 섞으면 왜곡됨.
나머지는 분류에 따라 갈린다:

- `sale_success_rate` / `sale_insufficient_stock_rate` / `sale_lock_conflict_rate`:
  정상적인 비즈니스 분기 비율(201 / 409-재고부족 / 409-락충돌). 몇 %든 그 자체로
  문제는 아님 — smoke는 재고를 일부러 부족하게 잡아서 insufficient_stock이
  나오는 게 오히려 의도된 결과다.
- `sale_client_error_rate`: 400(검증 실패)/404(존재하지 않는 리소스) 비율.
  **0이어야 정상** — 여기 잡히면 서버가 아니라 **스크립트가 보낸 요청 자체가
  잘못됐다**는 뜻이다(서버 결함인 `sale_server_error_rate`와 반드시 구분해서 볼 것).
- `sale_server_error_rate`: 5xx 비율. **smoke/load/02b/03b 전부 0이어야 정상.**
  0이 아니면 실제 서버 결함(대개 데드락)이므로 최우선으로 봐야 한다.
- `sale_connection_error_rate`: 응답 자체를 못 받은 비율(연결 실패/타임아웃).
  stress에서 VU가 10(HikariCP 풀 크기)을 크게 넘는 구간부터 올라가기 시작하면
  풀 크기가 병목이라는 뜻. `sale_connection_error_codes`(`{error_code, error}`
  태그)로 원인까지 갈라볼 수 있다 — 타임아웃(느려지다가 못 버팀, 큐잉 문제)과
  연결거부(리스너/OS 레벨에서 아예 안 받아줌)는 서로 다른 결론으로 이어진다.
- `sale_error_messages`: `sale_client_error_rate`/`sale_server_error_rate`가
  0이 아닐 때 원인을 메시지별로 쪼개서 보여준다(`{message: "...", status: "500"}`
  태그). 500 하나로 뭉뚱그리지 않고 "어떤 에러가 몇 건인지"를 바로 구분할 수
  있다 — 데드락처럼 여러 원인이 섞일 수 있는 5xx를 진단할 때 특히 필요.
- `sale_auth_error_count`: 401/403이 하나라도 찍히면 테스트 자체가 잘못된 것
  (토큰 만료, 계정 오류 등) — 서버 결함이 아니라 테스트 셋업 문제라는 신호.
- 마지막 `[stress] 초기재고=... 최종재고=...` 로그와 재고 음수 체크
  (`최종 재고는 절대 음수가 될 수 없음`)가 실패하면, 그건 곧바로 락에 실제
  버그가 있다는 뜻이므로 다른 무엇보다 먼저 봐야 한다.

## 발견된 버그: 매출/매입/결제 등록 시 partner 행 데드락 (2026-08-16, 수정 완료)

`01-smoke.js`를 처음 돌렸을 때 원래 기대(1명 성공 + 2명 409-재고부족)와 다르게
2명이 500으로 실패했다. `sale_server_error_rate`가 66% 근처로 튀었고, 서버
로그엔 `Deadlock found when trying to get lock; try restarting transaction`.
`SHOW ENGINE INNODB STATUS`로 MySQL이 실제로 감지한 락 대기 그래프를 직접
확인해서 원인을 확정했다 — 추측이 아니라 실측이다.

**쉬운 설명**: 직원 A(트랜잭션1)가 매출 전표를 등록하면서, 먼저 "이 거래처
정보를 참조한다"는 표시(공유 잠금)를 거래처 파일에 붙인다. 그다음 재고 창고
열쇠(item_spec)를 가지러 가는데, 그 열쇠는 이미 직원 B(트랜잭션2)가 들고 있다
— A는 B를 기다린다. 직원 B는 재고 창고 열쇠를 먼저 들고 자기 일을 마친 뒤,
이제 원장에 반영하려고 거래처 파일을 통째로 꺼내려는데(배타 잠금), 그 파일엔
이미 A가 붙여놓은 "참조 중" 표시가 남아있어서 통째로 못 꺼낸다 — B는 A를
기다린다. 서로가 상대방을 기다리며 아무도 못 움직이는 상태(교착)가 되고,
MySQL이 둘 중 하나(여기선 A)를 강제로 실패시켜서 풀어준다.

**코드 레벨 원인**: `OptimisticLockSaleService.register()`의 실행 순서가

```
1. saleMapper.insert(sale)                    ← sale.partner_id가 partner를 FK로
                                                  참조 → partner에 공유 잠금 자동 획득
2. 재고 차감 루프(item_spec에 배타 잠금)
3. ledgerService.recordReceivableChange(...)  ← partner에 배타 잠금 필요
```
로 되어 있어서, **공유 잠금을 쥔 채로 나중에 같은 행에 배타 잠금 승격을
요청하는** 구조가 됐다. 4단계 때 `sale_item`/`item_spec` 사이에서 이미 한 번
겪고 고쳤던 것과 정확히 같은 종류의 문제(자식 INSERT의 FK 공유 잠금이 부모의
배타 잠금 요청과 순서가 꼬임)가, 이번엔 `sale`/`partner` 사이에서 재발한 것이다.

**영향 범위**: 같은 순서 결함이 register 계열 4곳 전부에 있다(`cancel` 계열은
새 자식 행을 안 만들어서 이 문제와 무관):
- `OptimisticLockSaleService.register()`
- `PessimisticLockSaleService.register()`
- `PurchaseService.register()`
- `PaymentService.register()`

**재현 방법**: `k6 run k6/01-smoke.js` 또는
`./gradlew integrationTest`(`SaleConcurrencyIntegrationTest.optimisticLock_concurrentSales_neverOversellEvenUnderConflictRetries`)
— 둘 다 100% 재현됨.

**별개로 발견한 문제(데드락과 무관, 같이 수정함)**: `pessimisticLock_concurrentSales_neverOversell`
테스트의 `cleanUp()`이 `partner`를 지우려다 `ledger_entry`의 FK 제약에 걸려
실패했다 — 5단계로 테이블이 하나 늘었는데 테스트 정리 순서가 그걸 반영 못
한 것. `cleanUp()`에서 `partner` 삭제보다 먼저 `ledger_entry`를 지우도록 수정.

### 수정 (Before / After)

`LedgerService`를 "잔액 조정"과 "이력 기록" 두 단계로 쪼갰다.

**Before** — 한 번에 잔액 조정 + 이력 기록을 다 하는 메서드 하나뿐:
```java
// LedgerService
public void recordReceivableChange(partnerId, changeType, amount, docType, docId, userId) {
    partnerMapper.adjustReceivableBalance(partnerId, amount);
    Partner partner = partnerMapper.findById(partnerId)...;
    insertEntry(partnerId, RECEIVABLE, changeType, amount, partner.getReceivableBalance(), docType, docId, userId);
}

// OptimisticLockSaleService.register() — 문제의 순서
saleMapper.insert(sale);                 // ① partner에 공유 잠금 (FK 체크)
for (item) { 재고 차감; saleItemMapper.insert(item); }
ledgerService.recordReceivableChange(...);  // ② partner에 배타 잠금 필요 ← ①과 충돌 가능
```

**After** — 잔액 조정(이른 시점)과 이력 기록(늦은 시점)을 분리해서, 잔액
조정을 자식 행 insert보다 먼저 실행하도록 순서를 바꿨다:
```java
// LedgerService — 두 메서드로 분리
public BigDecimal adjustReceivableBalance(partnerId, amount) {   // 잔액만, 전표 ID 불필요
    partnerMapper.adjustReceivableBalance(partnerId, amount);
    return partnerMapper.findById(partnerId)....getReceivableBalance();
}
public void recordEntry(partnerId, ledgerType, changeType, amount, balanceAfter, docType, docId, userId) {
    insertEntry(...);   // 이력만, 잔액 미변경
}
// recordReceivableChange/recordPayableChange는 위 두 메서드를 합친 편의 메서드로
// 남겨서 cancel() 계열(자식 행 insert가 없어 이 문제와 무관)에서 계속 사용

// OptimisticLockSaleService.register() — 수정된 순서
BigDecimal balanceAfter = ledgerService.adjustReceivableBalance(partnerId, totalAmount);  // ① partner 배타 잠금 선점
saleMapper.insert(sale);                 // ② 이제 안전 — 이미 배타 잠금을 쥐고 있어 공유 잠금 요청이 즉시 통과
for (item) { 재고 차감; saleItemMapper.insert(item); }
ledgerService.recordEntry(partnerId, RECEIVABLE, changeType, totalAmount, balanceAfter, "SALE", sale.getId(), userId);  // ③ 전표 ID 확보 후 이력 기록
```

같은 패턴을 `PessimisticLockSaleService`/`PurchaseService`/`PaymentService`
4곳 전부에 적용. 각 서비스 테스트에 Mockito `InOrder`로 "잔액 조정이 전표
insert보다 먼저 호출된다"를 직접 검증하는 assertion을 추가.

**검증 결과**: `SaleConcurrencyIntegrationTest`(JUnit, 실제 MySQL) 통과.
`k6 run k6/01-smoke.js` 재실행 결과 — `sale_server_error_rate` 66%→**0%**,
`sale_lock_conflict_rate`(정상적인 409) 0%→**66%**로 정확히 전환됨(오버셀
없이 정상 동작 확인, 최종 재고 음수 체크도 통과).

## 서버 내부 지표 (actuator, 2026-08-16 추가)

`02`/`02b`/`03`/`03b`는 부하와 **같은 실행 안에서** `server_probe` 시나리오(1 VU,
1초 간격)로 actuator를 폴링해 서버 내부 상태를 함께 남긴다. 별도 수집 스크립트나
CSV 정렬이 필요 없고, 같은 리포트에서 같은 시간축으로 비교할 수 있다.

| 지표 | 읽는 법 |
|---|---|
| `server_hikari_active` | 실제로 쓰인 커넥션 수(최대 10) |
| `server_hikari_pending` | **0보다 크면 커넥션 풀이 병목**이라는 직접 증거 |
| `server_tomcat_busy` | 처리 중인 요청 스레드(최대 200). 폴링 자신이 +1 포함 |
| `server_heap_used_mb` | 힙 사용량. 소크 테스트에서 계속 우상향하면 누수 의심 |

`01-smoke.js`는 요청 3건짜리 정합성 확인이라 서버 지표가 의미 없어 붙이지 않았다.

**임계값 주의**: 폴링 요청도 `http_req_duration`에 잡히므로, 임계값은
`http_req_duration{scenario:sustained_load}`처럼 부하 시나리오로 범위를 좁혀야 한다.
안 좁히면 훨씬 빠른 폴링 요청이 섞여서 p95가 실제보다 낙관적으로 나온다.

- **커넥션 풀은 이 구간에서 병목이 아니다.** `pending`이 전 구간 0이고 `active`가

- **`item_spec` 락 충돌은 두 시나리오가 같다**(32% vs 33%). 규격은 양쪽 다 하나를

한계: 각 1회 측정이라 분산을 모른다. k6·앱·MySQL이 같은 PC에 있어 절대 수치는
쓸 수 없다(`LOAD_TEST_PLAN.md` 1절). 두 값의 방향성 정도로만 읽어야 한다.

## A1: 낙관적 락 vs 비관적 락 비교 (2026-08-16)

4단계에서 전략 패턴으로 두 구현을 만들어뒀지만 `SaleController`가 낙관적 락으로
고정되어 있어 비교가 불가능했다. `myerp.sale.lock-strategy` 설정으로 컨트롤러가 쓸
구현을 고를 수 있게 하고(`SaleLockStrategyConfig`), 같은 빌드·같은 스크립트로 양쪽을
측정했다.

```bash
./gradlew.bat bootRun --args='--myerp.sale.lock-strategy=pessimistic'
```

설정이 실제로 먹었는지는 `sale_lock_conflict_rate`로 확인된다 — 비관적 락에서는
409 충돌이 구조적으로 발생하지 않으므로 0%가 아니면 전환이 안 된 것이다.

### 결과 A: 여유 있는 부하 (`02-load.js`, VU 8, 45초)

| | 낙관적 락 | 비관적 락 |
|---|---|---|
| 성공률 | 68.15% | **100%** |
| 락 충돌(409) | 31.84% | 0% |
| p95 | **24.79ms** | 27.10ms |
| 실제 등록된 매출 | 1,479건 | **2,207건** |
| 실질 처리량 | 32.9건/s | **49.0건/s (+49%)** |
| `server_hikari_pending` | 0 | 0 |

### 결과 B: 한계 부하 (`03-stress.js`, 0→100 VU 램프, 120초)

| | 낙관적 락 | 비관적 락 |
|---|---|---|
| 성공률 | **12.54%** | **100%** |
| 락 충돌(409) | 87.45% | 0% |
| p95 | **640ms** | 838ms |
| 최대 응답시간 | 2.99초 | 5.23초 |
| 실제 등록된 매출 | 2,127건 | **12,592건** |
| 실질 처리량 | 17.7건/s | **104.9건/s (5.9배)** |
| `server_hikari_active` | 10 (포화) | 10 (포화) |
| `server_hikari_pending` (max) | 89 | 90 |
| `server_tomcat_busy` (max) | 100 | 101 |
| 5xx / 연결 실패 | 0 | 0 |

### 읽은 것

**응답시간만 보면 낙관적 락이 이긴다. 실제로 끝낸 일을 보면 정반대다.**
한계 부하에서 낙관적 락의 p95가 640ms로 비관적 락(838ms)보다 빠르지만, 그건 요청의
87%를 409로 되돌려보내서 얻은 숫자다. 같은 시간에 실제로 등록된 매출은 비관적 락이
**5.9배** 많다. p95 하나만 보고 전략을 고르면 정확히 반대 결론에 도달한다.

**두 전략은 자원을 똑같이 쓰고, 다르게 무너진다.** 커넥션 풀 포화(active 10,
pending 최대 ~90)와 Tomcat 스레드(최대 ~100)가 양쪽이 사실상 동일하다. 자원 병목은
락 전략과 무관하고, 갈리는 건 **그 자원으로 무엇을 끝냈는가**다.
- 낙관적 락 = **빠르게 실패한다.** 재시도 3회를 소진하고 409. 사용자는 빨리
  응답받지만 일은 안 끝났고, 재시도 비용은 서버가 이미 지불했다.
- 비관적 락 = **느리게 성공한다.** 대기가 쌓여 최대 5.2초까지 갔지만 한 건도
  실패하지 않았다.

**경합이 심해질수록 격차가 벌어진다.** VU 8에서는 1.5배 차이였는데 VU 100에서는
5.9배가 됐다. 낙관적 락의 충돌률도 32% → 87%로 뛴다.

### 한계 (결론을 일반화하면 안 되는 이유)

- **모든 요청이 규격 1개에 몰리는 시나리오다.** 실제 매출은 여러 품목에 흩어지고,
  그 경우 낙관적 락은 충돌이 거의 없어 재시도 비용 없이 빠른 쪽이 된다. 이 결과는
  "핫 로우가 있을 때"의 이야기다 — 경합도를 바꿔가며 어디서 역전되는지 보는 것이
  `LOAD_TEST_PLAN.md`의 A3다.
- 각 조건 1회 측정이라 분산을 모른다.
- k6·앱·MySQL이 같은 PC에 있어 절대 수치는 쓸 수 없다(`LOAD_TEST_PLAN.md` 1절).
  두 전략의 상대 비교로만 읽어야 한다.
- 낙관적 락의 409는 클라이언트가 재시도하면 결국 성공한다. 여기서 센 "실질
  처리량"은 **1회 시도 기준**이다.

## A2: 커넥션 풀 크기 스윕 (2026-08-17)

A1에서 VU 100일 때 풀이 완전 포화(active 10, pending 최대 90)되는 것을 보고,
**"풀이 병목이니 늘리면 되지 않나"**를 확인한 실험이다. 풀 크기만 10/20/50/100으로
바꾸고 나머지는 전부 고정했다(비관적 락, `03-stress.js`, 0→100 VU 램프 120초).

재현: `bash k6/run-pool-sweep.sh` (회차마다 actuator로 풀 크기 반영 여부를 검증하고
불일치면 즉시 중단한다 — 잘못된 조건으로 재는 사고를 막기 위함).

### 결과

| 풀 크기 | 실제 등록된 매출 | p95 | `pending` (max) | `active` (max) | 전체 CPU (avg) | mysqld CPU (avg) |
|---|---|---|---|---|---|---|
| 10 | 12,738건 | 836ms | 90 | 10 | 11.9% | 2.7% |
| 20 | 12,796건 | 809ms | 80 | 20 | 11.1% | 2.6% |
| 50 | 12,751건 | 704ms | 50 | 50 | 11.9% | 2.0% |
| 100 | **12,861건** | 713ms | **0** | 100 | 11.4% | 2.1% |

### 읽은 것

**풀을 10배 늘려도 처리량은 1%도 안 움직였다.** 12,738 → 12,861건, 오차 범위다.
그런데 `pending`은 90에서 **0**으로 완전히 사라졌다. 겉보기 지표는 깨끗해졌는데
시스템이 처리한 일의 양은 그대로다.

**대기가 없어진 게 아니라 장소를 옮겼다.** 풀 100에서는 커넥션을 기다리는 스레드가
하나도 없다. 대신 100개가 전부 커넥션을 쥔 채 InnoDB 안에서 같은 `item_spec` 행
잠금을 기다린다. Hikari 대기열이 InnoDB 대기열로 이동했을 뿐이다.

**그게 자원 부족 때문이 아니라는 건 CPU가 증명한다.** 전체 CPU는 어느 회차에서도
평균 11~12%였고 `mysqld`는 2~3%에 머물렀다. 커넥션 100개가 활성 상태인데 MySQL이
CPU를 거의 안 쓴다는 건, 그 연결들이 **일하는 게 아니라 잠금을 기다리며 놀고 있다**는
뜻이다. 한 PC에 세 컴포넌트를 몰아넣은 탓(자원 경쟁)이라는 대안 설명은 이 수치로
배제된다.

**처리량 상한은 풀이 아니라 잠금 보유 시간이 정한다.** 약 12,800건을 120초에
처리했으니 초당 약 107건이고, 행 하나를 한 번에 한 트랜잭션만 잡을 수 있으므로
잠금 보유 시간은 건당 약 9ms로 역산된다(1000ms ÷ 107). 이 구조에서 처리량을 올리려면
커넥션을 늘리는 게 아니라 **잠금을 쥐고 있는 시간을 줄여야 한다.** (역산값이라
직접 측정으로 확인이 필요하다.)

p95는 836ms → 704ms로 15% 정도 개선됐지만 풀 50에서 이미 평평해진다. 대기열을 두 번
(Hikari → InnoDB) 거치던 것이 한 번으로 줄어든 정도의 효과로 보인다.

### 어느 행이 상한을 정하는가 — `03` vs `03b`

`03-stress.js`는 거래처와 규격을 모두 하나씩 공유하기 때문에, 107건/s를 정한 것이
`partner` 행인지 `item_spec` 행인지 구분되지 않았다. `partner`는 데드락 수정으로 인해
트랜잭션 맨 앞에서 잠기고 커밋까지 유지되므로 더 오래 잡히고, 그래서 `partner`가
유력한 후보로 보였다. 거래처만 분산하는 `03b`로 확인했다(비관적 락, 풀 10, 동일 조건).

| | 공유하는 것 | 실제 등록된 매출 |
|---|---|---|
| `03` | 거래처 1개 + 규격 1개 | 12,738건 |
| `03b` | 거래처 100개(분산) + 규격 1개 | 11,879건 |

**거래처 경합을 완전히 제거했는데 처리량이 늘지 않았다**(오히려 7% 낮으나 1회 측정
오차 범위). 즉 상한을 정하는 것은 `partner`가 아니라 **두 시나리오 모두에서 끝까지
공유된 `item_spec`(재고) 행**이다. 잠금을 더 오래 쥐고 있다고 해서 그 행이 병목이
되는 건 아니고, **경합이 실제로 몰리는 행**이 병목이 된다.

이 결과는 VU 8에서 본 `02` vs `02b` 결과(거래처 잠금이 p95를 24.4ms → 18.3ms로
낮춤)와 모순되지 않는다. 거래처 경합은 **지연**에는 영향을 주지만, 포화 상태의
**처리량 상한**은 재고 행이 정한다.

### 이 결과가 말하는 것

**지표가 좋아진 것과 시스템이 나아진 것은 다르다.** `pending`만 보고 풀을 키웠다면
"병목을 해결했다"고 보고했을 텐데, 실제로 처리된 매출은 한 건도 늘지 않았다.
계측 없이 손잡이부터 돌리면 증상만 옮기고 끝난다.

### 한계

- 규격 하나에 전부 몰리는 시나리오다. 실제처럼 여러 품목에 흩어지면 행 잠금 경합
  자체가 사라지므로 결론이 달라진다(A3에서 확인 예정).
- 각 조건 1회 측정이다.
- 잠금 보유 시간 9ms는 처리량에서 역산한 값이지 직접 잰 값이 아니다.
- `k6` 프로세스 CPU 표본이 회차당 55~64개로 다른 지표(135개)보다 적다. 성능 카운터
  인스턴스가 간헐적으로 안 잡힌 것으로 보이며, 잡힌 표본은 전부 1% 안팎이라 결론에는
  영향이 없다.

### 측정 도구에 대한 기록

CPU 샘플러(`sample-process-cpu.ps1`)를 두 번 갈아엎었다.

1. `Get-Process`의 CPU 차분을 스크립트 안에서 계산 → **전 구간 0%**. 유휴 상태에서만
   스모크 테스트해서 "정상인데 한가함"과 "고장"을 구분하지 못한 채 스윕을 한 번
   통째로 낭비했다. **측정 도구는 부하가 걸린 상태에서 검증해야 한다.**
2. 누적 CPU 초를 원본으로 기록하도록 수정 → `app`/`k6`는 잡혔지만 `mysqld`는 서비스
   계정 소유라 `TotalProcessorTime` 접근이 거부됐다.
3. CIM 성능 카운터(`Win32_PerfFormattedData_*`)로 전환 → 세 프로세스 모두 권한 문제
   없이 읽히고 전체 CPU도 함께 얻는다.

부수 확인: **k6 자체의 CPU 사용률은 1% 안팎이다.** 부하 생성기가 결과를 왜곡할
만큼 자원을 먹는다는 우려는 이 워크로드에서는 실측으로 배제된다.

## A3: 경합도 스윕 — 그리고 진짜 천장을 찾다 (2026-08-17)

A1(낙관 vs 비관)과 A2(풀 크기)의 결론이 전부 "규격 하나에 전부 몰릴 때"라는 단서를
달고 있었다. 경합을 흩뜨리면 어디서 결론이 뒤집히는지 보려고 규격 개수를
1/10/100으로 바꿔가며 두 락 전략을 모두 측정했다(`run-contention-sweep.sh`).

### 결과 A: 경합도 × 락 전략

| 규격 수 | 비관적 (실제 매출) | 낙관적 (실제 매출) | 낙관적 충돌률 |
|---|---|---|---|
| 1 | 12,931건 | 2,151건 | 87.8% |
| 10 | 14,191건 | 10,427건 | 27.8% |
| 100 | **14,291건** | 13,235건 | **0%** |

**낙관적 락은 경합이 사라지자 6.2배 회복했다**(2,151 → 13,235건). 규격 100개에서는
충돌이 완전히 0%가 된다. A1에서 "낙관적 락이 87%를 실패시킨다"고 한 것이 락 전략의
결함이 아니라 **경합 조건의 산물**이었음이 확인된다.

예상이 빗나간 곳이 두 군데다.

1. **낙관적 락이 비관적 락을 역전하지 못했다.** 충돌이 0%인데도 여전히 8% 뒤진다
   (13,235 vs 14,291). 재시도 비용이 사라져도 앞서지 못한다는 것은, 두 전략의 차이가
   더 이상 처리량을 좌우하지 않는 다른 제약이 있다는 신호다.
2. **비관적 락의 처리량이 10%밖에 안 늘었다.** 재고 행이 천장이라면 행을 100개로
   흩뜨렸을 때 천장도 크게 올라야 하는데 12,931 → 14,291에 그쳤다. **재고 행도
   진짜 천장이 아니었다.**

### 결과 B: 두 제약을 동시에 풀어보기

6회차 모두 `server_hikari_pending`이 평균 25.7, 최대 88~90으로 **똑같았다.** 풀 10이
항상 포화다. 그렇다면 A2와 A3는 각각 제약을 하나씩만 푼 실험이었다는 뜻이다 —
A2는 경합을 최대로 둔 채 풀만, A3는 풀을 10으로 둔 채 경합만. 둘 다 풀면 뛰어야 한다.

| 조건 | 실제 매출 |
|---|---|
| 풀 10 + 규격 100 (비관) | 14,291건 |
| **풀 100 + 규격 100 (비관)** | **13,249건** |
| 풀 100 + 규격 100 (낙관) | 13,249건(성공률 99.99%) |

**또 빗나갔다.** 둘 다 풀었는데 오히려 낮다. 커넥션 대기 0, 락 충돌 0, CPU 17~22%인데
처리량은 그대로다.

### 진짜 천장: 커밋 내구성(fsync)

클라이언트 쪽 숫자를 Little's law로 맞춰보면 그림이 잡힌다. 램프 구간 평균 VU는 약 35,
평균 응답시간 316ms → 35 ÷ 0.316 = **111/s**로 실측(113/s)과 일치한다. 그리고 VU 5짜리
짧은 실행에서도 처리량은 똑같이 **113/s**였다(응답시간만 44ms). **VU를 7배 늘려도
처리량은 그대로고 응답시간만 비례해 늘어난다** — 서비스율이 고정된 자원이 포화됐다는
전형적인 신호이며, 초당 113건은 건당 **8.8ms**에 해당한다.

무엇이 8.8ms를 쓰는지 MySQL 상태 카운터로 직접 셌다(VU 20, 30초, 규격 100개):

| 항목 | 값 |
|---|---|
| 커밋 수 | 3,753 |
| `Innodb_os_log_fsyncs` 증가 | 6,929 → 커밋당 **1.85회** |
| `Innodb_data_fsyncs` 증가 | 7,645 → 커밋당 2.04회 |
| 합계 | 커밋당 약 **3.9회 fsync** |

109.6 커밋/s × 3.9 = 초당 약 426 fsync → fsync당 약 2.3ms(소비자용 SSD의 전형값).
커밋당 3.9회면 약 9ms로, 역산한 8.8ms와 맞아떨어진다.

원인은 서버 설정에 있다: `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` +
바이너리 로그 활성. 커밋마다 리두 로그와 바이너리 로그를 각각 디스크에 동기화하고
2단계 커밋으로 조율한다. 게다가 리두 로그 fsync가 커밋당 1.85회라는 건 **그룹 커밋이
사실상 묶어주지 못하고 있다**는 뜻이다(묶였다면 1보다 훨씬 작아야 한다).

### 세 실험을 관통하는 결론

처리량은 **풀 크기(10↔100), 경합도(규격 1↔100), 락 전략(비관↔낙관)을 어떻게 바꿔도
초당 110~119건에서 움직이지 않았다.** 후보를 하나씩 배제한 결과 남은 것은 커밋의
디스크 동기화 비용이다.

| 후보 | 판정 | 근거 |
|---|---|---|
| 커넥션 풀 | ❌ | 10→100, 처리량 1% 미변(A2) |
| 행 잠금 경합 | ❌ | 규격 1→100, 충돌 0%인데 10%만 증가(A3) |
| 락 전략 | ❌ | 경합 제거 시 두 전략이 8% 이내로 수렴 |
| CPU·메모리 | ❌ | 전체 17~22%, mysqld 3% |
| 부하 생성기(k6) | ❌ | 1% 안팎 |
| **커밋 fsync** | ✅ | 커밋당 3.9회 × 약 2.3ms ≈ 9ms ≈ 관측된 상한의 역수 |

**A1과 A2의 결론은 취소되지 않는다.** 규격 하나에 몰리는 조건에서는 행 잠금이 실제로
지배적이었고(낙관적 락 성공률 12.5%), 풀을 키워도 소용없다는 것도 사실이다. 다만 그
조건을 걷어내고 나면 **그 아래에 더 낮은 천장이 하나 더 있었다**는 것이 A3의 발견이다.

### 한계

- fsync 지연 2.3ms는 커밋 수와 fsync 수에서 역산한 값이지 직접 잰 것이 아니다.
- 결정적 검증(내구성 설정을 완화해 처리량이 뛰는지 확인)은 아직 하지 않았다.
  `innodb_flush_log_at_trx_commit`와 `sync_binlog`는 전역 설정이라 서버 전체의 내구성
  보장을 바꾸는 일이므로, 사용자 확인 없이 건드리지 않았다.
- 각 조건 1회 측정이다.
- 이 상한은 **이 PC의 디스크 특성**이다. 절대 수치를 다른 환경에 옮길 수 없다
  (`LOAD_TEST_PLAN.md` 1절).

## HTML 리포트

각 스크립트는 실행이 끝나면 터미널 요약(기존과 동일)에 더해 `k6/reports/`
아래에 그 스크립트 이름으로 HTML 리포트를 남긴다(`k6-reporter` 사용). 예:
`k6 run k6/01-smoke.js` → `k6/reports/01-smoke.html`.

`reports/` 디렉터리는 실행할 때마다 새로 생기는 산출물이라 `.gitignore`에
등록되어 있다 — 커밋되지 않는다. 브라우저로 열어서 스테이지별 그래프를
바로 볼 수 있고, `02`/`02b`(또는 `03`/`03b`) 결과를 나란히 열어두면
비교하기 쉽다.
